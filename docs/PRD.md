# PRD — 의류 가격 추적 및 할인 분석 서비스

> 상태: 초안 v0.1 (2026-11-18) · 코드 작성 전 단계
> 관련 문서: [architecture.md](architecture.md) · [database.md](database.md) · [wireframe.md](wireframe.md)

## 1. 배경과 목적

의류 쇼핑 플랫폼(무신사, 29CM, W컨셉 등)은 상시 할인·쿠폰·기획전이 많아서 "지금 할인가가 정말 싼지" 판단하기 어렵다. 표시된 할인율은 정가 기준이라 실제 거래 가격 흐름을 반영하지 못한다.

이 서비스는 **직접 수집한 가격 이력**을 근거로 현재가가 과거 대비 얼마나 저렴한지 보여준다.

### 핵심 질문 (서비스가 답해야 하는 것)

1. 이 상품(사이즈·색상까지)의 지금 가격은 얼마인가?
2. 내가 수집한 기간 중 최저가는 얼마였고, 지금은 그보다 몇 % 비싼가 또는 싼가?
3. 최근 30일·90일 최저가와 비교하면 어떤가? 그 판단에 쓸 데이터는 충분한가?
4. 같은 상품을 다른 플랫폼에서는 얼마에 파는가?

## 2. 범위

### 2.1 MVP 범위 (In scope)

| 항목 | 내용 |
|---|---|
| 플랫폼 | **1개**만 지원. 정책 검토 후 결정하며, 검토 전에는 샘플 데이터로 개발한다 |
| 상품 수 | 테스트 상품 10~20개 |
| 사용자 | 단일 사용자(본인). 로그인 없이 운영하되 쓰기 작업은 서버에서만 수행 |
| 가격 수집 | 허용된 방식(공식 API, 제휴 피드, 수동 입력, 샘플)만 사용 |
| 화면 | 대시보드, 상품 목록·검색, 상품 등록, 상품 상세(그래프·통계), 수집 상태 |

### 2.2 MVP 제외 (Out of scope, 확장 대상)

- 가격 하락 알림 (이메일, 푸시) → 테이블과 인터페이스만 설계
- AI 분석 (구매 타이밍 해석, 요약) → 저장 구조와 UI 구분 원칙만 설계
- 다중 사용자, 회원가입, 개인별 관심 목록
- 2개 이상 플랫폼의 자동 수집 (플랫폼별 가격 비교 화면은 수동·샘플 데이터로 먼저 구현)
- 쿠폰·적립금·카드 할인을 적용한 "최종 결제가" 계산

## 3. 핵심 원칙 (모든 기능에 적용)

| # | 원칙 | 구현상 의미 |
|---|---|---|
| P1 | **수집하지 않은 과거 가격을 만들지 않는다** | 보간·추정값을 DB에 저장하지 않는다. 그래프에서 수집 공백은 선을 끊어 표시한다. 30일 데이터가 없으면 "30일 최저가"를 표시하지 않고 "데이터 부족"으로 표시한다 |
| P2 | **변형(variant) 단위로 가격을 관리한다** | 가격은 `상품 → 색상·사이즈 변형 → 플랫폼 판매 옵션` 단위로 저장한다. 모델번호(품번)로 동일 상품을 식별한다 |
| P3 | **AI 해석과 수집 데이터를 분리한다** | AI 결과는 별도 테이블에 저장하고, 화면에서는 "AI 해석" 라벨과 근거 데이터 범위를 함께 표시한다. 가격 수치는 항상 DB 원본에서 렌더링한다 |
| P4 | **데이터 출처를 항상 표시한다** | 모든 가격 기록에 `source`(sample / manual / api / crawl)를 저장한다. 샘플 데이터는 화면에 "샘플" 배지를 표시한다 |
| P5 | **허용된 범위에서만 수집한다** | 플랫폼별 이용약관과 robots.txt, API 제공 여부를 검토하고 결과를 기록한 뒤에만 자동 수집을 켠다 |
| P6 | **실패와 부족을 숨기지 않는다** | 수집 실패, 오래된 데이터(stale), 데이터 부족 상태를 화면에 명시한다 |

## 4. 기능 요구사항

우선순위: **P0** = MVP 필수 · **P1** = MVP 이후 바로 · **P2** = 확장

### F1. 상품 검색 및 등록 — P0

- F1-1 상품명, 브랜드명, 모델번호로 **등록된 상품** 검색 (P0)
- F1-2 상품 URL을 입력하면 플랫폼과 외부 상품 ID를 파싱하여 등록 (P0)
  - 자동 수집이 불가능한 플랫폼이면 상품 정보(이름, 브랜드, 모델번호, 옵션)를 수동으로 입력받는다
- F1-3 색상·사이즈 변형 등록 및 플랫폼 옵션과의 매핑 (P0)
- F1-4 같은 URL·외부 ID의 중복 등록 방지 (P0)
- F1-5 플랫폼 내 키워드 검색으로 상품 찾기 (P2, 플랫폼 API가 허용할 때만)

### F2. 가격 수집 — P0 (수동·샘플) / P1 (자동)

- F2-1 수동 가격 입력: 확인한 시각, 정가, 판매가, 재고 상태 (P0)
- F2-2 샘플 데이터 시드: 개발과 데모용. `source='sample'`로 구분 (P0)
- F2-3 플랫폼 어댑터를 통한 자동 수집 (P1, 정책 검토 통과 시)
- F2-4 수집 주기 스케줄링 (P1, 기본 1일 1~4회)
- F2-5 수집 시도별 성공·실패 기록 (P0. 수동 입력도 기록 대상)

### F3. 가격 이력 저장 — P0

- F3-1 변형 단위로 수집 시각(UTC `timestamptz`)과 가격을 저장
- F3-2 정가(`list_price`)와 판매가(`sale_price`)를 분리 저장. 회원가·쿠폰가는 선택 필드로 따로 저장하고 기본 비교에는 쓰지 않는다
- F3-3 가격 기록은 **추가만** 한다(append-only). 잘못 입력한 기록은 삭제하지 않고 `is_void` 처리한다

### F4. 가격 비교 통계 — P0

| 지표 | 정의 | 표시 조건 |
|---|---|---|
| 현재가 | 가장 최근 **성공** 수집의 판매가 | 마지막 성공이 24시간보다 오래되면 "오래된 데이터" 경고 |
| 수집 기간 최저가 | 전체 유효 기록 중 최저 판매가와 그 날짜 | 기록 1개 이상 |
| 30일 최저가 | 최근 30일 유효 기록 중 최저 판매가 | 첫 기록이 30일 이전이고 30일 구간 수집 커버리지가 기준 이상일 때. 아니면 "데이터 부족 (N일 수집)" |
| 90일 최저가 | 위와 같으며 기간만 90일 | 위와 같음 |
| 최저가 대비 | `(현재가 − 최저가) / 최저가 × 100` | 해당 최저가가 표시될 때만 |
| 정가 대비 할인율 | `(정가 − 판매가) / 정가 × 100` | 플랫폼 표기 할인율과 별개로 계산 |

- 커버리지 기준(초안): 해당 구간의 일(KST) 중 **수집 성공일 비율 ≥ 70%**. 기준은 설정값으로 둔다.
- "역대 최저가"라는 표현은 쓰지 않는다. 항상 "**수집 기간 중** 최저가"라고 쓴다.

### F5. 가격 변동 그래프 — P0

- 변형별 판매가 라인 차트(Recharts), 정가는 보조선
- 기간 선택: 30일 / 90일 / 전체
- 수집 공백 구간은 선을 끊어 표시한다(`connectNulls=false`). 보간하지 않는다
- 수집 실패 시점은 마커로 표시 (P1)
- 샘플 데이터 구간은 배지 또는 범례로 구분

### F6. 플랫폼별 가격 비교 — P1

- 동일 변형(같은 모델번호 + 색상 + 사이즈)의 플랫폼별 현재가와 수집 기간 최저가를 표로 비교
- 플랫폼 간 상품 매칭은 **수동 연결**로 한다(자동 매칭은 P2)
- 플랫폼마다 마지막 수집 시각이 다르므로 시각을 함께 표시한다

### F7. 수집 실패 및 데이터 부족 표시 — P0

- 상품 카드와 상세 화면 상태: `정상` / `오래됨` / `수집 실패` / `데이터 부족` / `샘플`
- 수집 상태 화면: 최근 실행 목록, 실패 사유(HTTP 상태, 파싱 실패, 상품 삭제, 차단 의심 등), 연속 실패 횟수

### F8. 확장 구조 — P2 (설계만)

- 가격 하락 알림: 조건(목표가 이하, 최저가 갱신, N% 하락) 테이블과 평가 함수 인터페이스
- AI 분석: `ai_insights` 테이블, 모델·프롬프트 버전·입력 데이터 범위 기록, UI 분리 표시

## 5. 비기능 요구사항

| 항목 | 기준 |
|---|---|
| 성능 | 상품 상세 페이지 서버 응답 1초 이내 (상품 20개, 기록 수만 건 규모) |
| 정확성 | 통계 함수 단위 테스트 100% 통과. 표시값은 DB 원본과 일치 |

| 동기화 | PC와 노트북에서 `git pull` 후 `npm ci` + 환경변수 설정만으로 동일하게 실행 |
| 접근성 | 상태를 색상만으로 구분하지 않고 텍스트 라벨을 함께 표시 |

## 6. 데이터 수집 제약

> 아래는 **검토 체크리스트**다. 실제 허용 여부는 개발 착수 시점의 각 플랫폼 약관과 정책을 직접 확인해 [architecture.md §6](architecture.md#6-데이터-수집-정책-검토-절차)의 기록 양식에 남긴다.

| 확인 항목 | 무신사 | 29CM | W컨셉 |
|---|---|---|---|
| 공개 상품·가격 API 또는 제휴(어필리에이트) 피드 제공 여부 | 없음 (2026-11-18) | 미확인 | 미확인 |
| 이용약관의 자동 수집(크롤링·스크래핑) 관련 조항 | 원문 미확인 | 미확인 | 미확인 |
| robots.txt의 상품 페이지 경로 허용 여부 | **금지** (지정 봇 외 `Disallow: /`) | 미확인 | 미확인 |
| 로그인이 필요한 가격(회원가 등) 존재 여부 | 있음 | 미확인 | 미확인 |
| 봇 차단(캡차, WAF) 적용 여부 | **있음** (Cloudflare) | 미확인 | 미확인 |
| **결론** | **수동 입력** ([검토 문서](platform-reviews/musinsa.md)) | 미검토 | 미검토 |

**결정 규칙**

1. 공식 API·제휴 피드가 있으면 그것을 우선 사용한다.
2. 약관이 자동 수집을 금지하거나 robots.txt가 해당 경로를 막으면 **자동 수집을 구현하지 않는다**. 수동 입력과 샘플 데이터로 운영한다.
3. 허용되더라도 요청 간격을 두고(예: 상품당 하루 몇 회 이내), 식별 가능한 User-Agent를 쓰며, 로그인 우회·캡차 우회·차단 회피를 하지 않는다.
4. 수집한 원본 HTML이나 이미지를 재배포하지 않는다. 가격 수치와 최소한의 메타데이터만 저장한다.
5. 판단이 애매하면 해당 플랫폼은 수동 입력 모드로 둔다.

## 7. 샘플 데이터 정책

원칙 P1(과거 가격 생성 금지)과 "외부 연동 불가 시 샘플 데이터로 먼저 구현"을 함께 지키기 위해 다음 규칙을 둔다.

- 샘플 상품은 **가상 브랜드와 가상 상품명**을 쓴다(예: "SAMPLE 브랜드 A"). 실제 상품의 가격 이력처럼 보이지 않게 하기 위해서다.
- 모든 샘플 기록은 `source='sample'`이고, 화면에 항상 "샘플" 배지를 표시한다.
- 샘플 데이터는 별도 시드 파일로만 들어가며, 운영 DB에서는 한 번에 삭제할 수 있어야 한다.
- 샘플 시드에는 일부러 **공백 구간, 실패 기록, 30일 미만 상품**을 넣어 상태 표시를 검증한다.

## 8. 성공 기준 (MVP 완료 정의)

- [ ] 테스트 상품 10~20개가 변형 단위로 등록되어 있다
- [ ] 각 상품 상세에서 현재가, 수집 기간 최저가, 30일·90일 최저가(또는 "데이터 부족")가 정확히 표시된다
- [ ] 그래프에 공백 구간이 보간 없이 표시된다
- [ ] 수집 실패와 오래된 데이터 상태가 목록과 상세에 표시된다
- [ ] 샘플·수동·자동 기록의 출처가 화면에서 구분된다
- [ ] Vercel에 배포되어 있고, 다른 PC에서 clone 후 README 절차만으로 실행된다

## 10. 예상 기술적 문제와 대응

| 문제 | 영향 | 대응 |
|---|---|---|
| 플랫폼이 자동 수집을 허용하지 않음 | 자동 수집 불가 | 수동 입력·샘플 모드로 핵심 기능을 먼저 완성. 어댑터 구조로 나중에 교체 |
| 상품 페이지 구조 변경 | 파싱 실패 | 어댑터별 fixture 테스트, 실패를 `parse_error`로 기록하고 알림 |
| 가격 종류가 많음(정가, 할인가, 회원가, 쿠폰가) | 비교 기준 혼란 | 비교 기준은 로그인 없이 보이는 판매가로 고정하고 나머지는 별도 필드 |
| 옵션별 추가금 | 변형마다 가격이 다름 | 가격을 변형 단위로 저장 |
| 플랫폼 간 동일 상품 매칭 | 비교 오류 | 모델번호 기반 수동 연결. 자동 매칭은 후순위 |
| 서버리스 실행 시간·크론 빈도 제한 | 수집 누락 | 배치를 작게 쪼개고, 필요하면 GitHub Actions나 Supabase 스케줄러 사용 |
| 수집 공백 | 30·90일 통계 왜곡 | 커버리지 기준 미달이면 "데이터 부족" 표시 |
| 시간대 경계 | 일 단위 집계 오류 | UTC 저장, KST 기준 일 집계, 경계 테스트 |

## 11. 테스트 및 검증 기준

| 대상 | 방법 | 통과 기준 |
|---|---|---|
| 가격 통계 함수 | 단위 테스트(Vitest) | 빈 데이터, 기록 1개, 공백 구간, 동일 최저가 여러 번, void 기록, KST 자정 경계, 30일 미만 케이스 모두 통과 |
| URL 파서 | 단위 테스트 | 플랫폼별 정상·비정상 URL 판별 |
| 수집 어댑터 | 저장된 응답 fixture 기반 계약 테스트 | 실제 네트워크 없이 파싱 결과 일치. 실패 유형 분류 정확 |
| DB | 마이그레이션 적용 테스트, 제약조건 테스트 | 음수 가격, 중복 리스팅, 잘못된 enum 거부 |
| 화면 | 수동 체크리스트 → P1에서 Playwright E2E | 샘플 시드의 모든 상태가 화면에 표시됨 |
| 데이터 무결성 | 검증 SQL | 화면 표시값과 SQL 직접 계산값 일치 |
| 원칙 준수 | 코드 리뷰 체크리스트 | 보간값 저장 없음, AI 텍스트가 가격 수치를 대체하지 않음 |
